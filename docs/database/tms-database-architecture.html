Principal architecture reference

A relational system of record for a high-volume Transaction Management System.

PostgreSQL 16 as the single source of truth for organizations, devices, transactions, payments, reconciliation and settlement — engineered for 100,000+ IoT devices and 3.5M+ transactions/day, and designed to grow to 1M devices without a schema rewrite.

The one-paragraph verdict

Run Amazon Aurora PostgreSQL (writer + read replicas, Multi-AZ) as the system of record. Keep everything relational under logical schemas in one cluster. Make the transactions, transaction_status_history, audit_logs, device_logs and api_request_logs tables native range-partitioned by month. Absorb ingestion spikes through IoT Core → Lambda → SQS → batching workers behind RDS Proxy. Serve current device status from a small device_current_state table + Redis; serve the dashboard from pre-aggregated summary tables, never live scans of the billion-row history. Introduce TimescaleDB only for time-series aggregates, and sharding only past ~1M devices.

§1 · End to end

System architecture

Every device message is decoupled from the database by a queue. Nothing writes to PostgreSQL synchronously from the device path, so a 10× spike becomes queue depth — not a connection storm.

Why a queue sits between Lambda and PostgreSQL

Direct Lambda → PostgreSQL is an anti-pattern at this scale: a spike to thousands of concurrent Lambda invocations would each try to open a connection, exhausting the database. SQS turns a spike into backlog the workers drain at a controlled rate. Workers run at bounded concurrency, so peak DB connections stay flat regardless of device traffic.

What stays out of PostgreSQL

Raw MQTT frames, debug traces and per-request API logs go to CloudWatch / OpenTelemetry and S3, not the transactional store. PostgreSQL holds business truth: transactions, payments, state changes, audit and reconciliation. This keeps the hot tables lean and the working set in RAM.

Reading the peak

At 100K devices, 405 sustained peak TPS of small, idempotent inserts is comfortable for a single Aurora writer with batching — the risk is never raw TPS, it's connection count and unpartitioned table bloat. Both are solved structurally below, so the same design carries to 1M devices by scaling instance size, readers and partition cadence — not by redesigning.

§3 · Organization

One physical cluster, twelve logical schemas. This is recommended: schemas give namespacing, per-domain GRANTs and clear ownership boundaries without the cross-database join pain, distributed-transaction risk and connection multiplication of physically separate databases.

Benefit

Least-privilege DB roles per domain (a reporting role can't touch payment); tidy migrations; clear code ownership; and you can still JOIN freely across schemas in one transaction.

Search-path discipline and more qualified names. Avoid over-splitting — we do not make a schema per micro-feature. Twelve stable domains is the ceiling.

§6 · The critical table

Transactions & partitioning

The transaction table reaches 1.28B rows/year at 100K devices. It must never be one flat heap. Chosen: native PostgreSQL range partitioning by month on created_at — with TimescaleDB reserved for the reporting aggregates only.

A · Native range partitioning ✓ chosen

Monthly partitions transactions_2026_01…. Partition pruning turns every date-bounded query into a scan of one or two partitions. Old months detach and archive to S3 as immutable units. Full DDL/constraint control — critical for a financial ledger.

B · TimescaleDB hypertable

Excellent ergonomics and compression for append-only telemetry, but its value is time-series aggregation, not a mutable ledger with rich FKs and update-heavy status flows. We use it for continuous aggregates feeding the dashboard — not for the ledger itself.

C · Hybrid — what we actually ship

Ledger tables (transactions, transaction_status_history) → native monthly partitions. Dashboard rollups → TimescaleDB continuous aggregates (or plain summary tables if you skip Timescale). This keeps financial integrity native and hands the heavy read-aggregation to purpose-built machinery.

§7 · Exactly once, on top of at-least-once

Idempotency & concurrency

MQTT, Lambda, SQS and provider retries all deliver the same transaction 2–10 times. The database — not application memory — is the arbiter of "one transaction."

The guarantee

The device stamps a stable idempotency_key (or device_transaction_id) per logical transaction. The table carries UNIQUE (organization_id, idempotency_key, created_at). Workers use INSERT … ON CONFLICT DO NOTHING RETURNING:

  • First delivery → row inserted, returned, processed.
  • Duplicates → conflict, no row returned, ack & drop.

Result: N deliveries, exactly one row — enforced at the storage layer, immune to worker races.

The uniqueness ladder

  • idempotency_key — primary dedup, scoped per tenant.
  • device_transaction_id — unique per device (partial unique where not null).
  • provider_transaction_id — unique per provider on payments, catches provider-side dupes.
  • transaction_reference — human/business reference, indexed, not necessarily unique.
Concurrency without lock abuse

Status transitions use optimistic concurrency (a version column / WHERE status = expected) so two workers can't both move a row out of PROCESSING. Row locks (SELECT … FOR UPDATE) only where a genuine read-modify-write is unavoidable. Advisory locks only for singleton jobs (e.g. one recon batch per provider/day). No table locks, ever. The transaction_status_history table is append-only — transitions are inserts, never updates.

Correlation everywhere it earns its place

A single correlation_id (plus request_id, trace_id) is stamped at ingestion and threaded device → IoT → Lambda → SQS → worker → txn → provider. It's stored on transactions, *_status_history, *_failures, device_logs, audit_logs, notification_logs, alerts. It's not stored on static lookup tables — no value there.

Never in any log

Passwords, tokens, Authorization headers, full PANs, CVV, raw payment credentials. payment_provider_responses stores sanitized bodies with short retention. PII is minimized and column-encrypted where present.

Who created / updated a row

Attribution answers a different question than the timestamps: created_at/updated_at say when; these say who. Three kinds of actor are identified three ways.

ActorExampleIdentified by
Human userAdmin edits config, issues a refundcreated_by / updated_by → core.users, + audit_logs.user_id
DevicePOS raises a transactiondevice_id + provider + source (no human)
System / workerStatus auto-advances, recon jobsource + correlation_id (traces the pipeline)

Layer 1 — attribution columns (the "current" answer)

Every human-editable table (14 of them — orgs, users, roles, devices, providers, config, alert rules, settlement & recon batches…) carries nullable created_by and updated_by → core.users. Null means a machine did it. A stamp_row() BEFORE trigger fills them from a per-request session variable, so application code cannot forget to set them.

Layer 2 — audit_logs (the "history" answer)

Row columns only hold the latest editor. The append-only, partitioned audit.audit_logs keeps every change — action, old_value → new_value, user_id, IP, correlation_id — written by a generic audit.log_change() AFTER trigger. Earliest INSERT = creator; each UPDATE = an editor. entity_id is text so it holds both uuid and integer keys.

The contract

The app sets SET app.current_user='<uuid>' (and app.correlation_id) once per request — alongside the app.current_org that RLS already uses. From then on attribution and the audit trail are stamped in the database by trigger, not by hand. Device-driven tables (transactions, payments, *_logs) are intentionally excluded — their "who" is the device + trace id, read from transaction_status_history, not created_by.

§9 · Trust but verify

Reconciliation, settlement & the dashboard

Reconciliation

Provider files land in S3, ingest into reconciliation_batches → reconciliation_records, each carrying a match_status: MATCHED, MISMATCHED, MISSING_IN_TMS, MISSING_IN_PROVIDER, AMOUNT_MISMATCH, DUPLICATE, PENDING. Anything non-matched spawns a reconciliation_exception. Every record traces back to transaction → device → org → provider → settlement.

Settlement

settlement_batches group settlement_records that reference transactions and hold settlement-specific amounts (gross/fee/net) — without duplicating the ledger's authoritative financial fields. ON DELETE RESTRICT guarantees a settled transaction can never be deleted out from under a batch.

Dashboard — never scan a billion rows on page load

§10 · When to add what

Scaling roadmap

Everything below is in the design from day one except sharding. The point is thresholds — never introduce complexity before the number demands it.

StageDevicesIntroduceWhy now
1100KPartitioning, RDS Proxy, Redis, SQS, 1 read replica, summary tablesBaseline — all structural, cheap to run
2250K2nd/3rd read replica, PgBouncer tuning, weekly partitions, TimescaleDB aggregatesRead load and partition size climb
3500KSeparate reporting replica, S3 archival of cold partitions, larger writerAnalytics must stop competing with OLTP
41M+Aurora scale-up / limitless, dedicated data warehouse (Redshift), then consider tenant shardingSingle-writer ceiling & multi-TB hot set
Do not shard early

Sharding multiplies operational cost and breaks cross-tenant queries. A well-partitioned Aurora writer with read replicas comfortably serves 1M devices. Reach for sharding only when a single writer's write throughput is the proven bottleneck — and shard by organization_id so each tenant stays whole.

§11 · Keep it up, get it back

HA · DR · connections · security

Deployment: RDS vs Aurora vs self-managed

OptionStrengthsVerdict
RDS PostgreSQLSimple, cheaper, standard PGFine to start; single-writer, slower replica failover
Aurora PostgreSQLFast failover, up to 15 low-lag readers, storage auto-scales to 128 TB, RDS Proxy, backtrack✓ Recommended — read scaling + resilience at this volume
Self-managed EC2Full control, TimescaleDB/extensions freedomOnly if you need extensions Aurora lacks; heavy ops burden

Connection management

100K devices ≠ 100K DB connections. Devices hold MQTT sessions, not DB sessions. Fan-in collapses through RDS Proxy (+ PgBouncer transaction pooling), so a few hundred pooled connections back thousands of workers. Lambdas never hold DB connections directly — they enqueue to SQS. Worker concurrency is bounded, so peak DB connections are predictable.

Backup & DR targets

  • Continuous WAL + automated snapshots, PITR to any second in the window.
  • Cross-region replica / snapshot copy for regional DR.
  • RPO ≤ 1 min (continuous WAL), RTO ≤ 15 min (Aurora failover / promote).
  • Quarterly restore drills — an untested backup is a hope, not a plan.

Multi-tenancy & isolation

Every tenant-owned row carries organization_id. Enforce isolation at both layers: the API always filters by tenant (fast path), and PostgreSQL Row-Level Security is the backstop — a policy on organization_id vs a session SET app.current_org so a bug can't leak cross-tenant data. Belt and braces: RLS is the guarantee, the API filter is the performance path.

Integrity & security

  • PK/FK/UNIQUE/CHECK/NOT NULL throughout; money is numeric(18,4), never float; timestamps timestamptz in UTC.
  • ON DELETE RESTRICT from transactions to device/user — a financial row never disappears because a device was deleted. Soft-delete via deleted_at.
  • Encryption at rest (KMS) & in transit (TLS); secrets in Secrets Manager; per-schema least-privilege roles.

Final design review — passed

Scalability: partitioned billion-row tables, queue-buffered writes, pooled connections. Integrity: FKs, unique idempotency, RESTRICT on financial rows, numeric money. Performance: targeted indexes, partition pruning, pre-aggregated dashboard. Reliability: DB-enforced idempotency, optimistic concurrency, retry/DLQ. Logging: business in PG, telemetry in CloudWatch/S3. Security: dual-layer RLS, KMS/TLS, least-privilege roles, no secrets in logs. Ops: PITR, cross-region DR, RPO≤1m/RTO≤15m, tested restores, retention + archival.
